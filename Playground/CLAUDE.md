This project is mainly written in the programming language SmallJS, a Smalltalk dialect.
SmallJS source files have the extension: .st
Examples of SmallJS apps are in the folders : ../Examples, ../Browser, ../Node.
The SmallJS standard library is located in the folder: ../Smalltalk.

This is the Playground app: a web page where you can evaluate arbitrary SmallJS expressions
and see the results. Expressions are compiled and evaluated locally in the browser,
using a port of the SmallJS compiler that compiles to memory.
See `Playground.md` for a description of how it works.

## Source code

- All source code is in the folder: ./src
- `main.ts`: page entry point. Starts `PlaygroundApp`, or `TestPlaygroundApp` if the URL has `?test`.
- `PlaygroundApp.st`: the main app (binds the expression and result text areas and the evaluate button).
- `Playground.st`: evaluates an expression via the TS class `Evaluator` and returns the result or error to blocks.
- `Evaluator.ts`: wraps the expression in a temporary class `Evaluator` (method `evaluate`),
  compiles it to memory and runs it in a `<script type="module">` node on the page.
  It loads the compiled class info from `web/Script/CompiledClassesJson.js` to resolve class references.
  That file is generated by the SmallJS compiler.
  The expression is not prefixed with `^`: the ported compiler returns the value of the last statement.
- `Compiler/`: port of the SmallJS compiler (see below).
- `Test/TestPlaygroundApp.st`: test app (not a subclass of `Test`). Runs `TestPlayground all`,
  then GUI tests that click the evaluate button, then closes the window.
- `Test/TestPlayground.st`: unit tests for `Playground`.

## Compiler port

- The leading sources of the compiler are in `../Compiler/src`.
  The files in `./src/Compiler` are copies with a few Playground-specific changes.
  Search for the string "Playground" in these sources to find the adjusted code.
- Only the files needed to compile to memory are ported. `Compiler.ts`, `main.ts`,
  `DocumentedClassJson.ts` and `DocumentedMethodJson.ts` are not.
- `src/Compiler/SourceNode.ts` is unique to the Playground: a limited implementation of the
  npm package `source-node` that only manages source trees and does not generate source maps.
- The leading sources use CRLF line endings, the copies LF.
  To compare them, use `diff --strip-trailing-cr ../Compiler/src/<file> src/Compiler/<file>`.
- When the compiler changes, re-port it by overwriting the files with the same names
  and re-applying the Playground changes. Do this on specific requests only.

## Build and run

- `./build.sh`: compiles TypeScript (`tsc`, from `./src` to `./web/Script`) and then SmallJS:
  `../Compiler/start.sh -t ../Smalltalk/Core ../Smalltalk/Browser +t src web/Script`
  (`-t` skips the `Test` subfolders of the libraries, `+t` includes those of `./src`).
  Then it starts a web server on port 3000 and runs the tests in the browsers configured in `.env`
  (see `.env.example`). Without `.env` it skips the tests. Browsers close automatically if all tests succeed.
  At the end it kills the web server on port 3000.
- `./startWebServer.sh`: serves the folder `./web` at http://localhost:3000
  Open http://localhost:3000/?test to run the tests in the browser.
- `./clean.sh`: removes the generated files (`./web/Script`, and the obsolete `./web/Compiler`).
- `.vscode/launch.json` has Chrome and Edge launch configurations, with and without `?test`.

## Generated files

- `./web/Script` contains compiled output (JS and source maps, `CompiledClassesJson.js`, `Runtime.js`).
  Do not edit files there; edit ./src instead.
- The other files in `./web` are hand-written: `index.html`, `default.css`, `Logo.png`, `favicon.ico`.

## Coding style

- Do not end cascades with `yourself` when it is not necessary.
  In SmallJS a method without an explicit `^` return returns `self`,
  so a cascade ending with such a method (e.g. a setter) already returns the receiver.
  Only use `yourself` when the last message of the cascade returns another object.

## Testing

- Unit tests must not rely on user interaction, like allowing popups or permission prompts.
- Unit tests must not add entries to the session history of the test page (e.g. `pushState`),
  because then the test page cannot close itself after the tests.

### Running tests (for Claude)

Do not use `./build.sh` to run the tests: it starts and then kills the web server on port 3000.
Instead:

1. Compile if the sources changed:
   `tsc` and `../Compiler/start.sh -t ../Smalltalk/Core ../Smalltalk/Browser +t src web/Script`
2. Check for a web server on port 3000: `curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/`
   If none is running, start one in the background with `./startWebServer.sh`.
   Never terminate the web server after the run: it is left running for manual testing.
3. Run the tests only in headless Chrome, with a temporary profile folder outside this project:
   `timeout 60 "/c/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --disable-gpu
   --user-data-dir=<temp folder> --enable-logging=stderr http://localhost:3000/?test`
   Do not write the profile or log files into this project folder.
4. Check the console output (lines containing `CONSOLE`):
   - `Successfully run sync tests: N` and `Successfully run async tests: N` report the unit tests
     (N is the number of passed assertions).
   - Assertion errors report failures.
   - Chrome exits by itself (before the timeout) only if the GUI tests also pass,
     because the test app closes the window after all assertions succeed.
5. After every test run, report the number of passed sync and async tests.
